# STACK.md: Go + Huma (OpenAPI-first)

## Summary

A REST API where every operation is a typed Go function and the OpenAPI 3.1 document is generated from those types by
Huma v2: request/response schemas, validation, docs UI and client SDKs always match the code. Huma runs on top of a
router adapter (`humachi` for chi, or `humago` for the standard `ServeMux`) and returns RFC 9457 problem details for
errors. Hexagonal layout: Huma operations are adapters calling application services.

## Stack

| Layer | Choice | Why |
| --- | --- | --- |
| Language | Go 1.25+ | One static binary |
| API framework | `github.com/danielgtaylor/huma/v2` | Typed operations, OpenAPI 3.1 and JSON Schema generated, validation built in |
| Router | `go-chi/chi/v5` via `humachi` (or `net/http` via `humago`) | `net/http` compatible middleware |
| Errors | Huma's RFC 9457 problem details (`huma.Error404NotFound`…) | Standard error format |
| Database | PostgreSQL 16 | Relational, transactional |
| DB access | `jackc/pgx/v5` + `sqlc` | Hand-written SQL, type-safe Go |
| Migrations | `pressly/goose/v3` | Plain SQL, embedded |
| Config | env → typed struct (`caarlos0/env/v11`) | Validated at startup |
| Logging | `log/slog` | Structured |
| Clients | Generated from `openapi.yaml` (`openapi-typescript`, `oapi-codegen`, etc.) | Consumers never hand-write types |
| Contract checks | `oasdiff breaking` against the main branch | Breaking API changes are caught in CI |
| Testing | `testing`, `humatest`, `testcontainers-go` | Operations tested in-process |
| Lint | golangci-lint v2 + Spectral (OpenAPI lint) | Code and contract checked |
| Deploy | Static binary or minimal container | See the deploy add-on for the pipeline |

## Project layout

```
cmd/
  api/main.go                       config → db → services → chi router → humachi.New → register ops → server
  openapi/main.go                   writes openapi.yaml from the same registration (no server)
internal/
  config/config.go
  api/
    api.go                          huma.Config (title, version, security schemes), adapter creation
    register.go                     calls each feature's Register(api, deps)
  orders/
    order.go                        entity + invariants
    repository.go                   port
    service.go                      use cases
    api_types.go                    Input/Output structs with path/query/header/body tags and validation tags
    api_operations.go               huma.Register(api, huma.Operation{OperationID, Method, Path, Tags}, handler)
    postgres_repository.go          implements the port (sqlc)
  postgres/queries/ and db/         sqlc input and output
openapi.yaml                        generated, committed, diffed in CI
migrations/
```

Dependency direction: `api_operations → service → repository (port) ← postgres_repository`. Domain files import no Huma;
`api_types.go` is the only place request/response shapes live.

## Conventions

- Every operation has a stable `OperationID` (`list-orders`, `create-order`), tags, a summary and documented errors.
- Input structs use Huma tags: `path:"id"`, `query:"cursor"`, `header:"Idempotency-Key"`, `Body` field with `json`, `minLength`, `maximum`, `enum`, `format` tags; validation happens before the handler.
- Handlers return `(*Output, error)`; domain errors become `huma.Error4xx/5xx` in one mapping function.
- `openapi.yaml` is generated by `cmd/openapi` and committed; changing an operation means regenerating it in the same change.
- Pagination is cursor-based with a consistent `cursor`/`limit` pair; list responses carry `next_cursor`.
- Mutating operations accept an `Idempotency-Key` header where retries are possible.
- New endpoint = service method → input/output types → operation registration → regenerate spec → tests.

## Commands

| Task | Command |
| --- | --- |
| Run | `go run ./cmd/api` (docs at `/docs`) |
| Generate spec | `go run ./cmd/openapi > openapi.yaml` |
| Generate SQL code | `sqlc generate` |
| Breaking changes | `oasdiff breaking origin/main:openapi.yaml openapi.yaml` |
| Lint spec | `spectral lint openapi.yaml` |
| Test | `go test -race ./...` |
| Lint | `golangci-lint run` |
| Format | `gofmt -w .` |
| Migrate | `goose -dir migrations postgres "$DATABASE_URL" up` |

## Testing

- Operations: `humatest.New(t)` registers the operation with faked services; assert status, body and problem details.
- Validation: tests for invalid inputs prove the schema rejects them (no handler call).
- Services: unit tests with fakes; repositories: integration tests against Postgres.
- Contract: CI fails when `openapi.yaml` differs from the generated one or `oasdiff` finds a breaking change.

## Quality gates

- `gofmt`, `go vet`, `golangci-lint run` zero issues; `go test -race ./...` passes.
- Generated `openapi.yaml` and sqlc output are up to date; `spectral lint` clean; no unapproved breaking change.

## Dependencies

- Allowed: the table above.
- Do NOT use: hand-written OpenAPI files that drift from code, swaggo comment annotations, a second validation library for request bodies, ORMs.

## Rules for agents

- Never write request validation by hand when a Huma tag can express it.
- Never change an operation without regenerating and committing `openapi.yaml`.
- Never rename an `OperationID` or remove a field without a versioning decision: it breaks generated clients.
- Domain packages never import Huma; only `api_*.go` files do.
- Map domain errors to Huma errors in one function; never return raw errors to clients.
- Every operation documents its error responses and has a test for at least one error.
- Every query goes through sqlc.
- Keep `cmd/api` and `cmd/openapi` using the same registration function so the spec cannot drift.
