# STACK.md: Flutter + Firebase

## Summary

A Flutter app backed by Firebase: Authentication, Cloud Firestore, Cloud Functions (TypeScript), Storage, Crashlytics,
Remote Config and Analytics. Firestore is accessed only through repositories with typed converters, so the rest of the app
never sees `DocumentSnapshot` or `Map<String, dynamic>`. Security rules are code: versioned, tested against the emulator.
Two flavors (dev, prod) point to two separate Firebase projects.

## Stack

| Layer | Choice | Why |
| --- | --- | --- |
| App | Flutter stable, Dart 3.5+ | One codebase for iOS/Android/web |
| State / DI | `flutter_riverpod` + `riverpod_generator` | Streams from Firestore become `AsyncValue` providers |
| Navigation | `go_router` with auth redirect | Reacts to `authStateChanges()` |
| Models | `freezed` + `json_serializable` | Immutable, `withConverter` friendly |
| Auth | `firebase_auth` (+ `google_sign_in`, `sign_in_with_apple`) | Managed identity |
| Database | `cloud_firestore` with `withConverter<T>` | Typed reads/writes, offline cache |
| Files | `firebase_storage` | Uploads guarded by rules |
| Backend logic | Cloud Functions 2nd gen, TypeScript, `firebase-functions` v6 + `firebase-admin` | Trusted writes, triggers, integrations |
| Config | `firebase_remote_config` | Feature flags and kill switches |
| Monitoring | `firebase_crashlytics`, `firebase_analytics`, `firebase_performance` | Crashes, events, traces |
| Flavors | `flutterfire configure` per flavor → `firebase_options_dev.dart` / `_prod.dart` | Separate projects, no shared data |
| Local dev | Firebase Emulator Suite | Auth, Firestore, Functions, Storage offline |
| Testing | `flutter_test`, `mocktail`, `fake_cloud_firestore`, `@firebase/rules-unit-testing` | Rules and functions tested too |
| Lint | `very_good_analysis`; functions: ESLint + `typescript-eslint` strict | Strict both sides |

## Project layout

```
lib/
  main_dev.dart / main_prod.dart        Firebase.initializeApp(options: flavor options) + ProviderScope
  firebase_options_dev.dart             generated by flutterfire (never edited)
  firebase_options_prod.dart
  app/{app.dart, router.dart, theme/}
  core/
    firebase/firebase_providers.dart    providers for FirebaseAuth/Firestore/Storage instances
    firebase/converters.dart            Timestamp <-> DateTime JSON converters
    error/failure.dart                  sealed Failure (mapped from FirebaseException codes)
    remote_config/flags.dart            typed feature flags
  features/
    auth/{domain,data,presentation}/
    orders/
      domain/order.dart, order_repository.dart
      data/
        order_doc.dart                  Firestore DTO (freezed + json) + toDomain()
        firestore_order_repository.dart collection('orders').withConverter(...)
      presentation/orders_page.dart, orders_controller.dart
functions/                              Cloud Functions (TypeScript)
  src/index.ts                          exports only; one function per file below
  src/orders/onOrderCreated.ts
  src/orders/placeOrder.ts              callable, validates input with zod
  src/shared/{admin.ts, errors.ts}
  test/
firestore.rules
firestore.indexes.json
storage.rules
rules-tests/                            rules unit tests against the emulator
firebase.json / .firebaserc             projects: dev, prod
```

Dependency direction: `presentation → domain ← data`; only `data` imports `cloud_firestore`/`firebase_auth`. Functions never import app code; shared contracts are documented in the collection DTOs on both sides.

## Conventions

- Collections and fields in `camelCase`, collection names plural; document ids generated by Firestore unless a natural key exists.
- Every collection reference is created once in its repository with `withConverter`; no raw maps outside `data/`.
- Writes that must be trusted (prices, roles, counters, cross-document invariants) go through callable Functions or triggers, never from the client.
- Timestamps use `FieldValue.serverTimestamp()` on write.
- Every query has its composite index in `firestore.indexes.json` (committed).
- Firebase exceptions are mapped by `code` into `Failure` in the data layer.
- Functions: one function per file, input validated with `zod`, errors as `HttpsError` with stable codes; region set explicitly.
- New feature = domain + repository + converter DTO + rules + rules tests + indexes + UI.

## Commands

| Task | Command |
| --- | --- |
| Configure flavor | `flutterfire configure --project=<id> --out=lib/firebase_options_dev.dart` |
| Emulators | `firebase emulators:start --import=.emulator-data --export-on-exit` |
| Generate | `dart run build_runner build --delete-conflicting-outputs` |
| Run | `flutter run --flavor dev -t lib/main_dev.dart` |
| Test app | `flutter test` |
| Test rules | `firebase emulators:exec --only firestore "npm --prefix rules-tests test"` |
| Test functions | `npm --prefix functions test` |
| Lint | `flutter analyze && npm --prefix functions run lint` |
| Format | `dart format . && npm --prefix functions run format` |
| Deploy rules | `firebase deploy --only firestore:rules,firestore:indexes,storage -P dev` |
| Deploy functions | `firebase deploy --only functions -P dev` |

## Testing

- Repositories: `fake_cloud_firestore` and `firebase_auth_mocks` to test converters, queries and error mapping.
- Controllers and widgets: Riverpod overrides with `mocktail` repositories.
- Security rules: every collection has allow AND deny tests (owner, other user, anonymous, invalid fields) with `@firebase/rules-unit-testing`.
- Functions: unit tests for pure logic; integration tests against the emulator for triggers and callables.
- Critical flows with `integration_test` against the dev project or emulators, never prod.

## Quality gates

- `flutter analyze` and the functions' ESLint/`tsc --noEmit` with zero issues; formatters clean.
- App tests, rules tests and functions tests pass in CI (rules tests run in the emulator).
- `firestore.rules` changes require their tests in the same PR; no `allow read, write: if true` anywhere.
- Generated code committed and up to date; App Check enabled in prod.

## Dependencies

- FlutterFire official plugins, kept on the same BoM-aligned versions (update together).
- Functions: `firebase-functions`, `firebase-admin`, `zod`; anything else needs a reason.
- Do NOT use: client-side writes for trusted data, Realtime Database alongside Firestore without a reason, storing secrets in Remote Config or the app, Functions 1st gen for new code, `Map<String, dynamic>` outside the data layer.

## Rules for agents

- Never touch prod (`-P prod`) from a task; use the emulators or the dev project.
- Never edit `firebase_options_*.dart`: rerun `flutterfire configure`.
- Every new collection or field: update the converter, the rules, the rules tests and the indexes together.
- Never trust client data in rules: validate types, sizes and ownership (`request.auth.uid`).
- Reads use queries with limits and pagination (`limit`, `startAfterDocument`); no unbounded collection reads.
- Unsubscribe from snapshot streams when the provider is disposed (auto-dispose providers).
- Feature flags are read through `core/remote_config/flags.dart`, with safe defaults.
- Functions are idempotent (triggers can run twice): use the event id or transactions.
- Log with Crashlytics `recordError` for non-fatal errors; never log personal data.
