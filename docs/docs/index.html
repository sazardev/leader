Start · README.md

Overview

A Neovim config on top of NvChad v2.5, designed as a small framework: you clone it, run a script and get an editor ready to work, with what a developer uses every day and nothing more. Minimalism, fast productivity and performance: everything loads lazily, one file = one responsibility, and whatever you don't use is turned off with one line.

v1.3.0 · Neovim ≥ 0.11 · Linux, WSL, macOS and Windows · documentation

Installation

One command, everything done (Linux, WSL, macOS):

curl -fsSL https://raw.githubusercontent.com/sazardev/my-nvim-setup/master/install.sh | bash

Windows (PowerShell): irm https://raw.githubusercontent.com/sazardev/my-nvim-setup/master/install.ps1 | iex

It needs nothing from you: no clone, no prompts. It fetches the repo into ~/.local/share/my-nvim-setup and does everything (idempotent: run it again any time to bring it up to date):

  1. installs whatever is missing from the system (git, curl, C compiler, ripgrep, node, cmake) and Neovim ≥ 0.11 if you don't have it (in ~/.local/opt, without sudo; with brew on macOS);
  2. links nvim/ as your config (~/.config/nvim); an existing one is moved to nvim.bak-<date>, never deleted;
  3. enables the git hooks (.githooks: cheatsheet always up to date and conventional commits);
  4. writes your per-machine settings (nvim/lua/local.lua, git-ignored) if you pass the options below;
  5. installs the plugins at the versions pinned in nvim/lazy-lock.json (in parallel), the LSPs/formatters/linters (Mason) and builds the treesitter parsers (tree-sitter-cli comes from Mason), reporting the time each step took;
  6. sets up the AI agent with the best backend it finds (Claude Code, OpenCode, Ollama…); --agent none skips it.

Options go after bash -s --, for example a Go laptop, fully configured:

curl -fsSL https://raw.githubusercontent.com/sazardev/my-nvim-setup/master/install.sh | bash -s -- --lang go,lua --theme gruvbox

Prefer to clone it yourself (to hack on it)? git clone https://github.com/sazardev/my-nvim-setup && cd my-nvim-setup && ./install.sh does exactly the same. Override the fetch with NVIM_CONFIG_DIR, NVIM_CONFIG_REPO and NVIM_CONFIG_BRANCH.

Then open nvim. Press <Space> and which-key shows you the menus.

There is also a landing page, docs/index.html (flat and square like the config, no build, self-hosted Geist in docs/fonts/, dark/light with t), and the documentation at docs/docs/index.html (generated from the Markdown by scripts/gen-docs.sh); serve docs/ with GitHub Pages (cd docs && python3 -m http.server).

Native Windows (PowerShell): ./install.ps1 [-Lang go,typescript] [-Theme x] [-Light|-NoLight] [-Agent auto] [-NoPlugins] creates the junction at %LOCALAPPDATA%\nvim and does the same steps (written but not tested on real Windows; on WSL use install.sh).

Uninstall: delete the ~/.config/nvim link (and, if you want, ~/.local/share/nvim, ~/.local/state/nvim, ~/.cache/nvim).

Philosophy

  • Fast: ~20 ms startup (measured headless, with --startuptime); defaults.lazy = true, plugins loaded by event/filetype/command/key, bytecode cache (vim.loader) and unneeded built-in plugins disabled.
  • Minimal: 54 entries in lazy-lock.json, counting dependencies and NvChad's own. No heavy session manager, no tab bar, no embedded AI chat, no LSP dependency tree for things you don't use.
  • Modular: the config is declared, not wired. Adding a language, a plugin, an agent action or a Go helper means creating one file; nothing else is touched.
  • Spend the minimum: whatever can be decided without a model is decided beforehand (gates, local analysis, treesitter completion); when one has to be called, only what is needed is sent and the cost is shown.
  • Light where it matters: with ≤ 2 GB of RAM the resident processes (LSP, golangci-lint) are turned off automatically; force it with NVIM_LIGHT=1|0.
  • Everything by keyboard, with keys documented and generated from the real code.

Commits (<leader>G)

A single panel for committing: what goes in (staged vs not staged, with +/− per file), the message with live Conventional Commits validation (✔ feat(scope) · 38/72), assisted type and scope, and a line saying what the agent will do before spending anything. Gc opens the panel, Gm opens it with the AI draft, GM commits on its own, in the background (stages what is modified except sensitive files, the AI writes ONE message in English, it is validated and committed; if anything fails, it undoes what it staged) and Ga rewrites the last one. The AI message is always in English, on one line, in ~2 s with a light model.

AI agent (<leader>a)

It is not a plugin: it is Lua code in this config, with no dependencies, and it does nothing until you invoke it. Claude Code, OpenCode, Ollama (CPU/CUDA), LM Studio/llama.cpp/vLLM and other CLIs; it detects and configures its backends on its own (<leader>am → Setup, or ./scripts/agent-setup.sh). Customizing

Everything configurable is in nvim/lua/core/settings.lua with its default value and a comment. Your changes go in nvim/lua/local.lua (git-ignored, merged on top; the installer can generate it with --lang, --theme, --light):

-- nvim/lua/local.lua
return {
  theme = { name = "catppuccin" },
  languages = { disabled = { "astro", "dart", "java", "kotlin" } },
  agent = { backend = "ollama", tiers = { lens_security = "light" } },
  git = { commit = { subject_max = 60 } },
}

You do not have to edit a file for the everyday ones: <leader>Sp opens the settings panel (theme, motion, cursor, format on save, diagnostics layout, answer language, light mode, plugins, tools, update…). Enter flips a value and applies it at once when it can (the few that need a restart say so); your choices are kept apart (stdpath("state")/prefs.json), win over local.lua, and "Reset my choices" forgets them. Keys of their own: St theme, Sf format on save, Sl plugins, SM tools, Si info, Su update the config.

Files have the same treatment: <leader>F (and a / r / d inside the tree) creates, renames, moves, duplicates and deletes in flat modals that show where the file will land. Several files at once (a.go; b/c.go; d/), a name with / moves it, the move is a folder picker, and delete goes to a trash (<leader>Fu brings the last one back). Open buffers, language servers and the tree follow a rename; your unsaved changes survive it.

To add (each one is a single file and, at most, a name in its NAMES list):

  • a language: nvim/lua/languages/<name>.lua (contract at the top of languages/init.lua);
  • a plugin: a file in nvim/lua/plugins/<group>/;
  • a dashboard art: nvim/lua/ui/arts/<name>.lua (braille only);
  • an AI backend: an entry in agent.custom (no code) or nvim/lua/agent/backends/<name>.lua;
  • an agent action, lens or test: agent/actions/, agent/lenses/actions/ or agent/tests/actions/;
  • a per-language test convention: agent/tests/convention.lua;
  • a Go completion helper: a utils/go<name>.lua module on top of goindex and its call in gosmart.

How it is organized

The principles (the same across the whole repo) and where they show:

  • One responsibility per module: the pure parts (commit/conventional.lua, utils/goindex.lua, agent/protocol.lua) kept apart from what touches git, the LSP or the UI (commit/git.lua, commit/panel.lua); one presenter per output kind (agent/output/).
  • Open for extension, closed for modification: discovered registries (languages/, agent/actions/, agent/backends/, agent/lenses/); adding one doesn't force editing the others. The agent pipeline is extended with action hooks (retarget, merge, reveal, prepare), with guards (agent/guards/) and with events (agent/events.lua: verification, batches and the proposal queue subscribe; the presenter that accepts a proposal knows none of them).
  • Dependencies point to abstractions: each piece talks to a small contract (a backend's build/parser, a context provider's collect(target, done), a Go helper's declaration_items(range, frag)), not to its neighbor's implementation.
  • Configurable things in a single place: core/settings.lua; the scripts (install.sh, install.ps1) share the same settings logic (scripts/install-local.lua) instead of duplicating it.

How the leader works

Each language has its own letter under <leader> and only exists in buffers of that filetype; <leader>G (Git) only inside a repo, and <leader>a (agent), <leader>R (Makefile tasks), <leader>P (sessions), <leader>S (settings), <leader>F (files) and <leader>C (comments) are global. Press <leader> and which-key shows only what applies to the current file (no delay).

The language menus open an integrated terminal (toggleterm) and run the commands at the project root (they detect go.mod, package.json, Cargo.toml, pubspec.yaml, pom.xml/build.gradle...).

Workflows worth knowing

The exact keys are in CHEATSHEET.md; here, how they combine.

  • Jump and come back: after gd / grr / Ctrl+click, Esc returns to where you were (if you didn't edit there); it also closes popups and clears the highlight. Ctrl+o / Ctrl+i walk the jump history.
  • Line diagnostic (<leader>xd): opens a popup; press it again to enter it and copy the text.
  • Diagnostic blocks (utils/diagblocks.lua): <leader>xa draws all of them under their line (a bar in the severity color, source/code and a 2/5 counter); <leader>xc toggles between all expanded and one by one (each one a single line, only the one on the cursor line opens); <leader>xn/xp jump to the next/previous and turn the view on in one-by-one mode. They show up on their own in every buffer with diagnostics (the text on the right, virtual_text, is off) and <leader>xa turns them off in that buffer; then only the tinted line number remains. In insert mode the blocks are hidden (nothing appears or pushes the code while you type) and come back when you leave with Esc; diagnostics.update_in_insert = true keeps them live. Matched colors (ui/diagcolors.lua): the E2/W1 label in the status bar, the line number and each block's label are the SAME pill (background = the theme's DiagnosticError/Warn/Info/Hint, text = the theme background, bold), and the block's side bar uses that same accent; this way they change together with the theme (also with the theme inherited from the terminal and when Alacritty changes live: diagcolors.sync() detects the change on every status bar refresh and recomputes number and blocks, because base46 loads its cache without notifying through an event). Gutter: no icons either on the left or next to the code. The line number is drawn with the pill of the highest severity on the line (red error, yellow warning, blue info, cyan hint); the pill fits the digits, with a space on each side, so the number ends up centered (it is drawn by 'statuscolumn', defined in settings.options, and lines split by wrap only leave the gap) and git is a thin ┃ bar attached to the number (signcolumn=no: the statuscolumn draws the sign in ONE cell; with signcolumn=yes each sign takes two and an extra gap is left) (green added, blue changed, red deleted), so they are not confused. Your choice (<leader>xa on/off, <leader>xc expanded/collapsed) is global and saved in stdpath("state")/diagblocks.json, so it comes back the same when you reopen nvim; settings.diagnostic_blocks (auto, mode, number) only gives the initial value. <leader>xn/xp with the view off turn it on only in that buffer and don't touch what is saved. It updates on its own when diagnostics or the cursor change. The bottom panel (<leader>xx, Trouble) opens with focus: Enter jumps to the diagnostic and opens its popup, like <leader>xd.
  • Delete without clobbering the clipboard: <leader>d + motion (<leader>dd line, <leader>dw word) or in visual mode.
  • Multicursor (multicursor.nvim, real cursors like VS Code/Helix; loaded on the first key): add cursors by line (Ctrl+↑/↓), by match of the word or selection (Alt+n/Alt+p, Alt+Shift+n/p skips one) or all at once (Alt+a); Alt+click adds or removes one with the mouse. With several cursors everything (motions, operators, insert, undo) is repeated on each one; Esc clears them, Ctrl+q turns the main cursor off/on, ←/→ switch cursor and Alt+x deletes the current one. In insert mode, the secondary cursors replicate what was typed ON LEAVING insert; if the completion menu is open, Esc/jk close it first and you have to press them again. Ideas: Alt+a on a word to rename it in the file; Ctrl+↓ several times + I/A to edit columns. The native visual block (Ctrl+v + I/A/c) is still there for simple columns. Don't use Ctrl+n (it is nvim-tree).
  • Textobjects (treesitter): combine them with operators — daf deletes the function, dif the body, cif changes it, yaf copies it, vaf selects it; dac deletes the class. For braces of any block: di{ (inside), da{ (with braces), % jumps to the pair. PageDown/PageUp jump block by block (function, method, class, struct/interface in Go); they don't stop at closures inside a function, accept a count (3<PageDown>) and, with no blocks or no parser, do the normal scroll. Home/End go to the start/end of the current block; pressing them again goes up to the enclosing block (method → class → file). For start/end of line use ^/$ (or 0), and in insert they remain native.
  • Alt+hjkl move a line or block (mini.move); in Normal mode Alt+h is NvChad's horizontal terminal instead (the visual block still moves left).
  • Format: <leader>fm formats (conform); it also formats on save.
  • Telescope: the preview is always visible. flex layout: on the right in windows ≥ 110 columns, at the bottom in narrow ones (lua/plugins/navigation/telescope.lua).
  • nvim-tree: opening a file closes the tree; I shows/hides what git ignores. Deleting a folder warns how many files it contains.
  • Terminal: Alt+i (float), Alt+v (vertical) and Alt+h (horizontal) open NvChad's terminals, <leader>g… the toggleterm one. Esc (Terminal or its Normal mode) closes the window and the shell keeps running; Shift+Esc only hands the focus back to the previous window and leaves the terminal open. Shift+Esc needs a terminal that tells it apart from Esc; if yours doesn't, it behaves like Esc.
  • Completion (blink.cmp): the documentation appears instantly on selection and, for snippets, shows what will be inserted. Nothing comes preselected, except inside a Go struct tag (there Enter accepts the first suggestion). Sources: LSP, path, snippets, buffer; in Go gotags and gosmart are added; in Lua, lazydev.
    • With the menu open, Tab / Shift+Tab pick a suggestion (and Enter inserts it). Without a menu, inside a snippet (e.g. gorm.Open(dialector, opts)), they jump to the next / previous placeholder.
    • Keep what you typed and move on: Esc (closes the menu without leaving the snippet) and then Tab.
    • Esc (or jk) with the menu open only closes it and undoes the suggestion that was inserted (back to what you typed); you stay in insert mode and in your snippet. Without a menu, they leave insert as usual.
  • Sessions: one per folder (and per git branch; main/master use the base). They are not restored automatically: Restore Session button (rs) on the dashboard or its menu key. Opening a single file (nvim x) and quitting overwrites that folder's session; there is a key to not save on exit.
  • Git: git-blame is off by default (no cost); it is toggled from the Git menu.
  • Conventional commits (<leader>G, a single panel): Gc opens the panel, Gm opens it and immediately asks the AI for the draft, GM commits on its own, without a panel (see below), Ga rewrites the last commit (warns if it is already on the remote). At the top you see what gets committed: what is staged (●, with +/− per file) and, separately, what does not go in (○, modified or new); Space stages/unstages the file (or the whole group if you are on its header), a stages everything, u unstages everything, p or Enter show its diff. Below you write the message and the title is validated live (✔ feat(scope) · 38/72, or why it fails); Ctrl+t picks the type (suggested from the files) and Ctrl+o the scope (from the paths and the history). Underneath, a line says what the agent will do before spending anything (✦ AI claude/haiku · ⌃g to draft · reads 2 files, 3.1k chars: light model, only reads what is staged: its compact diff without lockfiles capped at git.commit.diff_max_chars, the branch and the list of types) and, when done, what it did (drafted by … · 2.5s · 1.2k→39 tok · $0.0001); Ctrl+g asks for the draft (never on its own, except with Gm), replaces the message and is undone with u, and repeating it gives another one. The message is always in English and on a single line (Conventional header; ~2 s with haiku). GM automatic commit: no panel and in the background; if you already staged files it commits only those, otherwise it stages everything modified except sensitive files (git.commit.sensitive: .env, keys…), the AI writes the message, it is validated and committed, and a one-line notice gives hash, message, files, +/−, time and cost. If something fails (no backend, AI, invalid header, a hook) it undoes what it staged and leaves nothing half done (Gm to do it by hand). Ctrl+s (or Enter in normal mode) commits; with nothing staged or with an invalid message it warns and does nothing; if a hook rejects the commit the panel stays open so you can fix it. Tab toggles files ↔ message, q/Esc cancel (and stop the agent). The .githooks/commit-msg hook requires the same format on any git commit (types and length in git.commit; if you change the list of types, change it in the hook too).
  • Comments (<leader>C): Cd inserts the idiomatic documentation template for the function/type under the cursor (godoc, LuaCATS, JSDoc, docstring, rustdoc) with name, parameters and return already filled in; Cm lists in quickfix the public items that have no doc comment (for other languages use the agent: <leader>ad). Snippets in any language, with the language's own comment style: todo, fixme, note, hack, warn, perf, deprecated (and with o at the end, e.g. todoo, TODO(name):); they live in nvim/snippets/all.json.
  • Theme: gruvbox ↔ gruvbox_light, or inherit the terminal's (Alacritty), which is followed live.
  • Other: :TSContext toggle pins the function/class context at the top; za/zc/zo fold (treesitter folds with nvim-ufo, everything open on start) and <leader>z folds by what the code is: <leader>zf the function you are in, zt the type, zo the object/table literal, zb the block (again = the one around it), zm the methods of the current type, zF/zT/zO every function/type/object in the file, za outline only, ze expand all, zs focus here (all closed except this), z1-z3 fold everything deeper than that level (all after <leader>); <leader>C folds long comments (blocks or consecutive // lines of comments.min_lines or more, 4 by default): Cc folds them all and remembers the preference (files you open afterwards, and future sessions, open with them already folded; it is saved in stdpath("state")/comments.json), Ce unfolds them and stops folding them automatically, Ct toggles only the one under the cursor without touching the preference; comments.auto_collapse only gives the initial value; :Lazy sync installs/updates plugins (the config auto-reload does not).

Light mode

On machines with ≤ 2 GB of RAM, LSP, go.nvim and golangci-lint are turned off (go vet remains). Treesitter, conform and nvim-lint keep running. Force it with NVIM_LIGHT=1|0. Per-machine settings in lua/local.lua (ignored by git).

  • Language: lua/languages/<name>.lua + add it to NAMES in languages/init.lua + its page here.
  • Plugin: one file in lua/plugins/<group>/.
  • New keymap: give it a desc of 2+ words starting with its section ("Harpoon add file"); the generator and NvCheatsheet group by the first word and drop single-word ones.

Features · docs/cheatsheets/agent.md

AI agent

One-shot actions on what you are looking at: a function, a class or a selection. No chat, no sidebar, no conversation. Every action has a closed prompt, a bounded context and an output with a fixed format, so it is predictable and cheap. Keys: CHEATSHEET.md (Agent menu).

Flow

  1. Put the cursor inside a function (or select lines in visual mode) and press <leader>a + the action.
  2. The code being sent is highlighted and a spinner turns on the right: ⠋ implement · claude/haiku · 1.2s.
  3. The result shows up in the code, depending on the action:
ActionInputResult
i implementfunction (its name, signature, doc or TODO are the spec) + optional instructioninline diff: deleted lines in red, added lines in green below. ⏎ accepts, ⎋ rejects
r reviewfunction or selectionreal findings as diagnostics on their line (◆); <leader>xd shows the detail
e explainfunction or selectionwindow next to the code, streaming; closes by itself when the cursor moves, or with Esc from the code (while it is still streaming, Esc also stops the call)
a askyour question (text field)window, same as explain
f fix inlinethe diagnostic (LSP, linter or agent finding) on the cursor line + optional hintdiff with the minimal change on only those lines; the surrounding code and the objects it points to (the variable's type, the signature of what is called) go along as read-only context; with no diagnostic on the line, it does nothing
F fix blockall the diagnostics of the function (or selection) + optional hintdiff with the minimal change that leaves the block coherent (several diagnostics with the same cause are fixed together)
d docsfunction + optional focusdiff that only adds/updates the documentation comment; the model returns only the comment (agent/docplace.lua puts it above the function, or inside it for Python), so the code cannot change and the output is a few lines
t convertselection (or the paragraph under the cursor) holding a JSON sample, a SQL CREATE TABLE or a curl command, in a code file + optional root type namediff that replaces it with ready code in the file's language: JSON → Go structs with json tags and nested types (TS interfaces, JSDoc typedefs in JavaScript, Python dataclasses, Rust serde structs, Dart classes with fromJson/toJson…), a table → a struct with db tags and pointers for nullable columns, curl → a function that sends the request with the standard client (secrets become parameters). What each source becomes is fixed per language (agent/convert.lua), so the prompt is explicit; light model, only rules as context. A one-word instruction names the root type (Invoice); in a non-code file it refuses (paste the JSON where the types should go). In Dart it follows pubspec.yaml: JSON → freezed classes (or @JsonSerializable()), a table → a drift Table; the import and part lines are added on accept (convert_header.lua on proposal.accepted, rules in utils/dartheader.lua) and a snake_case key left without @JsonKey(name: …) gets it by rule (Dart / Flutter)
n next editthe 30 lines around the cursor + what you just changed in this filediff with the ONE edit that follows from your recent changes (the rename you are following through, the field added to one constructor and not the others); with nothing changed in the file it asks nothing (Next edit)
R refactoryour instruction (text field)diff that applies exactly that instruction
g handoffyour instructionsends file:range + instruction to an agent already running in Herdr

The instruction field is inline (like the inline chat in Zed or VS Code): it opens right ABOVE the target code and pushes the code down instead of covering it, with an accent bar, a header (✦ implement · claude/sonnet) and a placeholder. It grows as you type (up to 6 rows), ⏎ sends, ⎋ cancels (also if you switch windows), ⌃J / Alt+Enter insert a line break and ↑/↓ (or ⌃P/⌃N) walk through the previous instructions of that action, which are remembered across sessions. In narrow windows the key hint shortens itself. There is no autocompletion or auto-closing of quotes inside.

Instruction: i, d, t and f open the field and Enter with an empty field runs without an instruction; if you type something, it is appended to the prompt and takes precedence over the default behaviour. Useful for an empty func main() {} ("read a CSV and sum column 3"), for an unclear function ("this validates orders before charging; the coupon case is missing") or to steer a fix. a ask and R refactor require the text; r review and e explain run instantly.

Short menu: i implement, d docs, t convert, n next edit, r review, e explain, a ask, f fix inline, F fix block, R refactor, g hand off (only inside Herdr), h history, m model (main, light and effort in a single selector), c clear (discards the finding on the line, or those in the selection in visual mode), C clear file (those in this file), x stop (cancels what is running and discards the pending proposals; it does not touch findings) and l last answer (reopens the last answer or rejected proposal). Everything that works on many pieces at once lives in its own Advanced menu, <leader>aA, so the everyday one stays short: a fix all, o / O fix from output / from a command, p plan across files, and for the proposals they leave waiting ] / [ next / previous, y accept all, l list. Accepting and rejecting a proposal have no menu entry: they are ⏎ and ⎋ on the proposal (and Tab refines it).

Accepting is a single change: u undoes it entirely. If you edit the code while the agent is working, the proposal is discarded instead of overwriting your change. Several actions can run at once (not on the same block).

Which target it takes

Priority: visual selection (always whole lines) > function under the cursor (with the contiguous comments above it, which are the spec) > class > paragraph of lines around the cursor (useful for a half-written signature: type func ParseConfig(path string) (*Config, error) and press <leader>ai). "Function/class" is the definition of af/ac (treesitter textobjects), for any language with a parser. More than context.max_target_lines (400) is rejected: trimming it would break the replacement.

Order of the prompt (stable first, volatile last)

The sections reach the prompt arranged by each provider's stability: 1 the same on every call of the project (rules, testing), 2 changes only when the code does (types, outline, contracts, schema, ports, ddd, testfile, callees), 3 changes with the cursor or the editor (diagnostics, findings, around, callers, gitlog, changes, subject). The declared order still decides what survives when the budget is tight; only what is SENT is rearranged. What this buys depends on the backend:

  • Ollama / llama.cpp / vLLM keep the KV cache of the last prompt and reuse what is identical from the start: a second action on the same code re-reads only the tail. For that, Ollama's num_ctx is now sticky per model (a small action after a big one keeps the big window, otherwise Ollama reloads the model and drops that cache).
  • claude -p gets almost nothing from it: the CLI sends the whole message as ONE block and the fixed part is under the cache's minimum size. That is why prompt_cache stays off (measured: -40% per call); if you turn it on, <leader>ah shows cache_read/cache_write per run so you can check it pays. The answer cache is what makes repeated questions free there.
  • A new provider declares stability = 1|2|3 next to its cap (default 2).

Pitfalls

  • A small local model fails more often with the structured format (code block, L<n>|sev|msg): use it for docs/explain and, if you want more, move up to a 14b+ code model. Esc rejects malformed output as usual.
  • Without a GPU the model runs on CPU: fine for the light tier; the report says whether what is loaded is on GPU, GPU+CPU or CPU.
  • WSL2: to reach the Windows Ollama, set OLLAMA_HOST=0.0.0.0 there. In Docker with NVIDIA: docker run -d --gpus all -p 11434:11434 -v ollama:/root/.ollama ollama/ollama.

Repository (<leader>aP): persistence adapters

Implementing a repository (SQL, Postgres, MySQL, in-memory...) is long but mechanical, and the model needs what is not in the file you are looking at. The agent finds it by itself, without you mentioning files, and each piece arrives with its path:

  • Port: the interface it must satisfy. It is deduced from the name (PostgresOrderRepository, pgOrderRepository, OrderRepositoryImpl, CachedOrderRepository → OrderRepository) and from what is declared explicitly (implements X, class T(X), impl X for T, var _ X = (*T)(nil)); it is located with ripgrep in any folder structure and read with treesitter.
  • What is missing: it compares the port's methods with those the type already has (in Go, the functions with that receiver in the package) and also warns about the constructor. Only the missing ones are requested.
  • Entity and types the port names (Order, with its fields and constants) even if the empty struct does not mention them: without this the model invents the fields.
  • Sibling example: another implementation in the project (the one in the same folder is preferred) with the constructor and the equivalent method: this way it copies your structure, your error handling (fmt.Errorf("…: %w"), errors.Is(err, sql.ErrNoRows)) and your mapping.
  • Schema: the entity's real table with its later changes and the dialect (from the schema syntax and from go.mod/package.json/pyproject/Cargo.toml/pom.xml), the access library and the parameter style. It is agnostic: with the same prompt, a Postgres migration produces $1 and ON CONFLICT, and a MySQL one, ? and ON DUPLICATE KEY UPDATE.

<leader>aPp (repo port) uses the type under the cursor (or that of its receiver, if you are inside one of its methods) and writes the type, the constructor and ALL the missing methods, in the port's order. <leader>aPi (repo implement) writes a single method with that context; implement (i/aDi) receives it too if the code is an adapter, and <leader>aPr (repo review) reviews what is specific to persistence (columns that do not match, dialect parameters, concatenated SQL, unclosed rows, unwrapped errors, N+1) and <leader>aPc (repo check, 0 tokens) compares the port's methods with those of the type and the entity's fields with the columns of its table. Silent if it does not apply: a service, a handler or any other function does not pay even for the search (measured: 0 characters of extra context).

Tested with Claude on an empty PostgresOrderRepository with a 4-method port: it returned the constructor and the 4 methods with the real columns from the migration, $1…, the error style of the sibling implementation and no invented fields (what it assumed, such as order.ErrNotFound, it states in note:), for ~$0.0013 with Haiku. Limits: the port is found by name or explicit declaration (not by type inference); the sibling example is the first reasonable one it finds; the schema is only read from *.sql and *.prisma (not from ORM models or the live database).

Service (<leader>aS): application services / use cases

A service can only call the methods that its ports declare. The ports provider finds the interfaces the service receives (fields, constructor parameters, method parameters, in any language) and reads them with their real signatures, each with its path and the instruction to call only those methods; with examples it adds another service of the project as a style example.

  • <leader>aSi service implement: orchestrates the domain and calls ONLY the ports in <ports> with their exact names and signatures; business rules are called on the entity (not reimplemented); it propagates the context and translates the ports' errors.
  • <leader>aSr service review: calls to port methods that do not exist or with wrong arguments, business rules in the service, leaking infrastructure details, swallowed or untranslated errors, non-atomic steps or steps ordered in a risky way (effects before saving), N+1.
  • <leader>aSd service deps (0 tokens): for each port, which methods it declares, which ones this file calls and which ones the port does NOT declare (it would not compile), which implementations it has and whether any is wired (used outside its file); it lists what needs attention.

Tested with Claude: on a service that called orders.FindByID (the port declares ByID), deps detected it without an LLM and service review flagged it against the real port; service implement used only ByID, Save and Mailer.Send and called the entity's o.Confirm() instead of repeating the rule (what it assumed, such as a method the entity does not have, it stated in note:).

Findings that stay (and how to fix them)

The findings of review and ddd review, and the violations of ddd diagnose, are diagnostics pending attention: they are saved (stdpath("state")/agent-findings.json) and come back when you open the file in another session, even if you do not deal with them today.

  • Each one is saved with the text of the flagged line. If the code has moved since then (you edited above, another branch...), it is relocated by that text (up to ±40 lines); if the line no longer exists, it is dropped with a warning (Agent: 1 saved finding no longer matches the code and was dropped). Saving the file updates the positions.
  • Only the agent's are saved: LSP ones are not touched. If there is no findings file, opening a file costs nothing.
  • Clearing them (from memory and from disk; review and ddd alike): <leader>ac clear discards the one on the cursor line (in visual mode, those in the selection) → one at a time; <leader>aC clear file, all those in this file; :AgentClear [file|all] (with a range: :'<,'>AgentClear), all = all files. <leader>aDc ddd clear, the DDD diagnostic of the whole project. <leader>ax stop does not delete them: it only cancels what is running and discards pending proposals.
  • Fixing them: <leader>af (fix inline, the one on the line), <leader>aF (fix block, the whole function) and <leader>aDf (ddd fix) read the findings that fall in the function or selection, together with the LSP diagnostics, and propose the minimal change (in ddd fix, respecting the layers in <ddd>; if the fix needs a port, type or file that does not exist, it says so in note: and does not invent its content). When you accept the proposal, the findings in that range are considered resolved and also disappear from what is saved. review and ddd review do not read earlier findings: a new review must not start from what the previous one said.
  • Flow: <leader>aDr (review) → tomorrow, another session: the diagnostics are still there → <leader>aDf on the function → ⏎.

What the local analysis does (free, no LLM): it walks the project once (asynchronously, in batches; it only reads files inside layer directories and that are not tests; cached by mtime) and deduces:

  • Layers by directory name (domain, application, infrastructure, interface and synonyms: usecases, adapters, persistence, api, handlers...; adjustable in settings.agent.ddd.layers). The dependency rule points inwards: domain ← application ← infrastructure / interface. Composition roots (main, cmd/, container, di...) may wire everything.
  • Violations (◈ diagnostics in the code + quickfix list + panel): outward dependencies (with the exact import), frameworks in domain/application (database/sql, net/http, gorm, @nestjs, sqlalchemy, org.springframework... per language: Go, TS/JS, Python, Java/Kotlin/Scala, Rust, C#, PHP, Dart) and badly named files (PaymentService in pricing.go).   • Naming: file style (snake_case, kebab-case, order.entity.ts, PascalCase) and most used roles (repository, service, handler...), deduced from what already exists; suggestions for missing files respect it.
  • Aggregates, gaps and connections: for each domain entity (a type with an ID field) it looks for its repository port, its implementation, whether it is wired (its name is used in some other file, via rg) and its use cases; it lists what is missing.

What the model receives (<ddd> section, max. 1800 characters, only what is relevant to that target): its layer and what it may depend on, project layers, naming convention with examples, neighbouring files, the pieces surrounding the entities it touches (Order: port OrderRepository (...) · impl PostgresOrderRepository (...) wired ✓ · use cases PlaceOrder), the violations in that file and a line with the idiom of the current language (constructors, errors, injection). Plus the DDD rules (~600 characters).

Measured on a Go project with one complete entity (port + implementation + use case) and another without a port: implement of Order.Confirm() used Pending/Confirmed (the constants of the Status type travel with it) and respected the layer; review found the *sql.DB and the concrete repository stuffed into the entity, plus primitives without invariant; missing listed the vertical slice of Customer with paths in the project's style. Each action, under $0.001 with Haiku. On a repo with 7500 code files, the first analysis takes ~0.9 s (252 layer files) and the next one 35 ms.

Limits: layers are recognised by directory name (if yours are named differently, adjust layers); "entity" is a domain type with an ID field; "wired" means "its name appears in another file", not a dependency-graph analysis; imports are read with regex and types with treesitter, so it is not a compiler. Languages without a treesitter parser only contribute imports.

History and spending (<leader>ah)

Every action is stored in stdpath("state")/agent-history.jsonl (append-only): when, action, model, target, your instruction, the system prompt, the exact message sent, the response, tokens (with cache read/write), cost, time and what you did with the result (accepted, rejected, discarded, N findings...). This way you can see transparently what was asked and what was paid.

  • <leader>ah opens a selector with one row per run (date, outcome, action, model, cost, target); the title adds up the total spent. The preview shows the full detail rendered as markdown, including the code sent (the target and the code around it, highlighted in its language); ⏎ opens it large and ⌫ (BS) comes back to the list with the same filters, search text and run selected.
  • ⌃F filters the history by agent (claude, opencode, ollama…), provider (who serves the model: anthropic, openai, local…), model, action, outcome or project: pick the dimension, then the value (each with its runs and cost). Filters stack and show in the title with the runs and spend that match; ⌃X clears them.
  • ⌃S opens the spending report (⌫ comes back to the list): by period (today, 7 days, total), by action, by model, by day, cost per applied change, what was spent on proposals you did not apply, errors, cache hits, where the prompt goes (system, context per provider, target) and the 5 most expensive runs. It is the basis for deciding what to cut.
  • ⌃Y copies EVERYTHING about the run as markdown (the same text you see in the detail): outcome and event line (accepted at 09:38:27...), target, time, tokens, cost, your instruction, the response, the system prompt and the exact message sent. ⌃P copies only the prompt (system + message) to reproduce or tweak it. In the detail panel and in the report panel, Y copies the whole panel. Everything goes to the clipboard (+) and the unnamed register.
  • Privacy: the history includes your code (it goes inside the prompt). agent.history.store_text = false stores only metrics; enabled = false turns it off. It compacts itself to the max_entries (1000) most recent.

Refine: change a proposal without starting over

A proposal is on screen and almost right? Tab (settings.agent.keys.refine) opens the instruction field again ("how should it change?") and replaces the proposal with a new one that starts from the previous code: the model sees the original target, the proposal and only what you ask to change. The old proposal never touched your buffer; the history links the new run to it. Cost: about one ordinary run per round (your instruction is ~30 tokens, the previous proposal 100-300), instead of rejecting and describing everything again.

The same key on an answer (explain / ask window) asks the next question about the same code with the earlier questions and answers as the conversation (the oldest turns are dropped past ~4k characters). The answer window never takes focus, so while it is on screen the key is also bound on the code buffer you are in (it goes away with the window; a proposal waiting in that buffer gets the key back). Pressing it needs no <leader>al first.

After accepting: verification

Accepting a proposal is no longer the end. agent/verify listens to the replace presenter's events and, for free:

  1. remembers the buffer's LSP and linter diagnostics before the code is written (the agent's own findings do not count: accepting resolves those);
  2. waits until the language server settles (verify.settle_ms, never more than verify.max_wait_ms) and compares: a diagnostic is identified by what it says (source, code, message), not by its line, so the same old warning one line lower is not new;
  3. nothing new → one quiet line ✓ verified · no new problems; something new → a question fix regression 1/2: it names the problems, the attempt, the model and the estimate. Yes launches a fix regression proposal over the function that holds them (same experience as any proposal, and verified again if you accept it); verify.max_retries (2) bounds the chain, verify.auto_retry = true skips the question (still bounded and still behind the spend guard);
  4. a build check (verify.command = "auto": go build ./..., cargo check, py_compile, dart analyze of the saved file in machine format (only its errors count, never warnings); or your own per language) runs when you save the accepted code, because a compiler reads the disk. Only the errors on or next to that code are blamed on it; the rest of the project's errors are counted, not guessed at.

Tokens: 0 unless you answer yes; then about 1.8 runs per attempt (the original prompt plus the errors). docs is excluded (verify = false: only comments change).

Several proposals at once

fix all, fix from output and multi-file plans share one engine (agent/batch):

  • One confirmation with the total (3 proposals · claude/sonnet · ~2.3k tokens · ~$0.0012, the files and how many problems each holds). The budget guard is not asked again per piece, but a hard cap still stops the rest.
  • The pieces run one by one; the statusline says ⠋ agent fix all 2/3. If you cancel (<leader>ax) or the budget blocks one, the rest does not go on.
  • Each piece is anchored (an extmark), so accepting something above it while it runs does not misplace it.
  • The proposals wait in a queue: <leader>aA] / <leader>aA[ jump between them across files, <leader>aAl lists them in the quickfix, <leader>aAy accepts them all after one question (each is its own u). Each proposal's hint ends with 2/4 · <leader>aA] next.

Fix all (<leader>aAa) groups the file's diagnostics by the function (else the type) that contains them: three findings in one function are one request. Sources and severity: settings.agent.fixall (agent findings, DDD violations, LSP/linters; warn and up by default). Tokens: about one fix block run per affected function (5 findings in 3 functions ≈ 3 runs).

Fix from output (<leader>aAo): the errors come from the last terminal buffer, else the quickfix list; <leader>aAO asks for a command (the project's build by default), runs it and uses what it prints. They are parsed by Neovim's own errorformat (go, tsc, cargo, python, javac, flutter analyze, dart analyze (human and --format=machine) and the generic file:line:col: message), 0 tokens; each piece sends only the errors of its function (<build_errors>), not the whole output. At most settings.agent.errors.max_errors (20) errors are read.

Multi-file plans

<leader>aAp on a type or function, then what should change ("add a Done flag to notes, through every layer"):

  1. Free: where it reaches. Language-server references (completed with git grep when the server never leaves the starting file), collapsed to the declarations that hold the symbol (function or type, with its first line as the signature), capped by settings.agent.plan (max_files, max_sites).
  2. One request: the instruction and only those signatures (never bodies; ~40 tokens per site) go to the model, which answers ordered steps n|path|symbol|what. Steps that name a file or symbol that is not in the list are dropped (the model inventing them).
  3. You: the plan panel (☑ 1. path · Symbol — what). Space unchecks a step, a all/none, Enter runs the checked ones, q cancels. Its first line keeps the estimate up to date as you toggle.
  4. One request per step, in order: each is a proposal for its declaration, with the overall plan (this step marked) and what the steps before it proposed as context, so step 3 uses the field that step 1 adds. They land in the queue above and are verified as you accept.

A snapshot (git stash create, nothing in your work tree changes) is taken first: git diff <ref> shows everything the plan changed and git checkout <ref> -- <file> restores a file. Renames are better done with LSP rename (deterministic, 0 tokens); the plan is for semantic changes. Tokens: plan ≈ 1-2.5k in, 300 out; each step ≈ 1 run; a 5-step plan is about 6 runs in total.

Spend guard

Before every request (actions, batches, the staged review, plans) the budget guard (agent/guards/budget.lua, pure core in agent/budget.lua) checks the size of what is about to be sent (characters ÷ 3.5 ≈ tokens) against settings.agent.budget and what the history says you already spent. The price of a token is learned from your own history with that model (no price table). Above confirm_tokens / confirm_usd, or near a cap, it asks (modal with the reasons); a used-up day_usd / session_usd blocks. Every one-shot call (commit draft, staged review, plan) is recorded in the history too, so the spend is complete. The usage report (<leader>ah → ⌃S) gains a Budget line and Suggestions: actions you accept rarely (and what they cost), the share of the spend that went to proposals nobody applied, and how often the verifier had to retry.

Review before committing

<leader>Gv (or ⌃R in the commit panel) reviews what is staged:

  1. Free checks on the added lines: secrets (AWS/GitHub/Slack/OpenAI-style keys, private keys, password = "…" literals), merge-conflict markers, debugger/print leftovers per language (not in tests) and sensitive files (settings.git.commit.sensitive).
  2. If there is real code to read (not only lockfiles, generated files, deletions or binaries) one request goes out with the staged diff numbered by its lines in the new file (+L13 added, L12 context), within git.commit.review_max_chars. A finding must point at one of those lines or it is dropped as invented.
  3. Findings land as diagnostics on their lines (open files at once; the others when you open them: they persist like any finding) with source staged review, and as a quickfix list. The panel's agent line says review: 2 findings (quickfix).

Tokens: a typical commit (40-200 changed lines) is ~1.5-6k in and 100-600 out; a docs-only or lockfile-only commit costs nothing.

Context for refactors and explanations

Project conventions: .agent.md

Next edit (on demand)

Not autocomplete and not ghost text: one key press (<leader>an) asks the light model (a small local one through light_backend is enough) for the edit you are about to make. What it sees: the lines around the cursor (settings.agent.next_edit.window, 30 each side) and <edits>, your latest changes in this file as -/+ hunks, oldest first.

  • The changes are tracked by agent/edits.lua: a baseline snapshot per file buffer, compared with the buffer when an insert ends or a normal-mode change settles (one vim.diff; no model, no LSP, files over next_edit.max_lines are not followed). It keeps the last keep hunks and sends at most max_chars of them (the newest win).
  • With nothing changed in the file it asks nothing (0 tokens, and says why). If nothing in the window clearly follows from your changes the model returns the window unchanged and you get "no changes".
  • It is a normal replace proposal: inline diff, ⏎/⎋, verification after accepting, history. Not cached (a proposal on live code).
  • Why on demand: a streaming ghost-text subscription spends tokens on every pause; this spends them only when you ask.

Answer cache (repeated questions are free)

A request is identified by everything the model would receive: system prompt, file, context sections, target, task, your instruction, plus backend, model and effort (agent/cache/, pure logic in cache/core.lua). If the same request was answered before, the stored answer comes back with 0 tokens, before the budget guard (nothing to ask about), and goes through the same presenter (the status line says cached · 0 tok · saved $…). A hit is not a run: it never appears in the history (<leader>ah) or the spend report, since no model was called. Any change to the function, to a type or diagnostic it reads, or to your instruction changes the hash, so a stale answer cannot come back.

  • Kept by default: text and findings outputs (explain, ask, review, lenses). A replace proposal is never cached: asking again on live code should give a fresh one. An action can opt in or out with cache = true|false.
  • Stored in stdpath("state")/agent-cache.json; the least recently used go past max_entries, and answers expire after ttl_days.
  • <leader>aAk shows what the cache holds and has saved you (answers kept, times it answered, tokens and money saved: counters the cache keeps itself) and has a Clear button. settings.agent.cache.enabled = false turns it off.
  • Tests must never share the real cache (a hit hides the call they count): K.fake() points it at a temp file.

Pitfalls

  • Generated files (*.g.dart, *.freezed.dart, *.gr.dart, *.mocks.dart, protobuf; list in utils/generated.lua) are rewritten on the next build: actions that edit (replace output) refuse to run there, explain/ask still work. They are also left out of types, code search and the architecture levels' searches.
  • If the model disobeys and sends several code blocks (draft + corrected version, 2 out of 6 times in a test with Rust), the last one that starts like the target is used and the hint warns: model sent 2 blocks, check the diff.
  • The accept/reject hint shortens in narrow windows (it drops tokens/cost first) and the spinner switches to a compact version.
  • The colors of the diff, the spinner, the hint and the window are derived from the active theme's palette with guaranteed minimum contrast (4.5:1 for text) and are recomputed when the theme changes (<leader>S); tested with the 97 base46 themes and the terminal-inherited theme. Findings use the diagnostic colors of your theme.
  • A visual selection is taken as whole lines.
  • Esc rejects the proposal while one is visible in the buffer (only then; settings.agent.keys changes it).
  • A model may return an empty block: it means deleting that range (e.g. fix removing unused imports).
  • needs-import: after the block is shown in the hint; imports are not added by themselves.
  • scripts/test-agent.sh runs the tests for parsers, target, local backends and setup (no network or tokens: the Ollama/OpenAI servers are fake, scripts/fake-llm.py).

Fix: two levels

  • <leader>af fix inline: put the cursor on the line with the diagnostic (the underline/block from LSP, linter or review). The target is only the diagnostic's lines (if it spans more than agent.context.diagnostic_lines, only what starts there). It carries as context: the full diagnostic, the agent.context.around lines before and after within its function (<around>, read-only), the signature of what it calls (<callees>) and the definitions of the objects it points to: for each identifier in the diagnostic (and the object of an x.Field access) the LSP is asked for its typeDefinition, so the model sees type Note struct even if the code does not name the type (n := load(); n.Titl). If the real fix lives elsewhere (an import, a missing declaration) it says so in needs-import: / note: instead of editing outside the lines. In visual mode, the selection is the target.
  • <leader>aF fix block: the target is the whole function (or the selection) and it fixes all its diagnostics at once, with the same type definitions. Use it when several diagnostics share a cause or the fix touches several lines.

The targets of the project's Makefile in one picker, run in the integrated terminal. It asks make, so it costs 0 tokens and nothing stays running. Keys: CHEATSHEET.md (section Run).

It works with a Makefile and only with a Makefile. Without one, every key says so and does nothing, except <leader>Rc, which creates one.

Which Makefile

The nearest GNUmakefile, makefile or Makefile from the current file's folder up to the git root, never above it (the ~/Makefile of the machine is not your project's). In a monorepo, a Makefile in the subfolder wins over the root's.

What is a task

A target is listed when it is .PHONY or has a description. Descriptions come from the file's text:

.PHONY: build test

build: ## Build everything        <- inline description
test: build
	go test ./...

# Remove the build output            <- a comment right above works too
clean:
	rm -rf out

.PHONY targets declared in included files are found too (the list comes from make -qp, which prints make's database and runs nothing). Without GNU make (Windows, BSD) only the file's text is parsed. A Makefile with neither .PHONY nor descriptions lists every plain target.

Features · docs/cheatsheets/gitignore.md

.gitignore

Writes a .gitignore from what the project is made of. 0 tokens, nothing resident. Keys: CHEATSHEET.md (section Git, ignore rules).

What it looks at

Marker files and extensions under the git root (3 levels deep; settings.git.ignore), never inside dependency or build folders (node_modules/, vendor/, target/… count by name only). go.mod or *.go → Go, package.json or *.ts → Node, pubspec.yaml → Dart/Flutter, Dockerfile → Docker, *.tf → Terraform… Nothing is read from file contents.

The checklist opens with what it found checked and says why (found go.mod +14). Secrets (.env*, keys, certificates, credentials, password databases) and Editor and system (OS files, IDE state, logs) are recommended for every project; Secrets goes first in the file, Editor and system last. Space or x toggles, a toggles all, Enter writes.

With a .gitignore already there

It adds only what is missing and never removes or reorders anything: a rule is not written twice (not even across topics: dist/ is in Node, Python and Go but lands once), a block with nothing new disappears with its comment, and a topic the file already covers is listed as already in .gitignore, unchecked. Each row says how many new rules it would add. It refuses to run while .gitignore has unsaved changes in a buffer.

What git already tracks

Ignoring a file does not untrack it. After writing, it asks git which tracked files the rules now match (git ls-files -ci --exclude-standard) and warns, e.g. a .env that was committed long ago: git rm --cached <file> stops tracking it (the secret stays in the history: rotate it).

Architecture

Neovim + NvChad v2.5 config — not an application. No CI or build system; the only automatic checks are scripts/gen-cheatsheet.sh --check and scripts/test-agent.sh (agent parsers and target, no network).

Uses scripts/install-mason.lua, scripts/install-treesitter.lua and install-local.lua; tests in scripts/test-install.sh; scripts/test.sh runs all the suites.
